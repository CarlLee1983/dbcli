效能調查 · SQL

慢 API 的第一步，
不是猜哪個索引少了。

讓 Agent 直接調整正式資料庫是高風險捷徑。先聚合觀測資料、讀查詢計畫、產生可審查的索引建議，才能把問題範圍縮小。

情境：某個 API 在尖峰時段變慢。你需要知道是不是同一種 SQL 重複發生、最慢查詢碰到哪些表，以及改動前應該檢查什麼。

安全工作流

從本機觀測事件找出模式

proxy analyze 讀取已記錄的事件，按 fingerprint、耗時、錯誤與熱門資料表聚合；它不會執行資料庫寫入。

dbcli proxy analyze --format json --top 10

確認結構，再看查詢計畫

先確認受影響表的實際 schema，再以 explain 蒐集執行證據。

dbcli schema orders --format json
dbcli explain "@saved-query" --format markdown

把索引提案留在審查階段

根據被確認的查詢取得缺失索引建議，然後交由 migration review 決定是否形成 DDL。

dbcli guide missing-index-for "@saved-query" --format json
dbcli skill tasks plan migration-review \
  --param "table=<精確資料表名稱>" \
  --param "ddl=<已擷取的 dry-run DDL>"

dbcli 不會替你做什麼

它不會根據單次查詢就自動建立索引，也不會把觀測結果當作效能結論。索引牽涉寫入成本、鎖定與部署策略，仍應由人審查。
