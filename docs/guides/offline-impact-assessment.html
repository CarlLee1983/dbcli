變更審查

要刪欄位時，先問「誰還在靠它做事？」

產品想拿掉一個舊欄位，migration 還沒寫。這時最有用的不是一句「看起來沒人在用」，而是把本機已知證據整理出來，也把不知道的地方明白標出來。

這次要審的變更：團隊準備刪欄位、改型別或調整關聯。release reviewer 想在討論 DDL 前先看：目前 schema 或 ORM 定義下，哪些 contract、saved query 名稱與驗證紀錄可能相關？

一份不假裝全知的影響報告

先決定拿哪個現況當基準

要看已知的資料庫樣子，就選 schema cache；要看 application model，就指定 ORM artifact。一次只選一種，報告才知道自己在和誰比較。

dbcli impact assess --design ./dbcli.design.json --against-cache --output ./impact.json --format json --fail-on warn

設計還在 model 階段，就完全離線地比 ORM

如果 PR 還沒產生 migration，直接指定 ORM 檔案。這條路不會連線，也不會偷偷更新 cache；適合在 code review 先把疑點列出來。

dbcli impact assess --design ./dbcli.design.json --against-orm ./prisma/schema.prisma --output ./impact.md --format markdown --fail-on never

把「沒有資料」也當成結果

報告會納入可用的 semantic contracts、saved-query 名稱、verification metadata 與已審閱 workload evidence。缺少、過期或讀不到的證據會成為 coverage gap；它提醒大家補查，不會替變更背書。

dbcli 不會替你做什麼

impact assess 不會連線、不會執行 SQL、不會更新 cache，也不會讀取 query body。v1 永不宣稱覆蓋完整；報告不是變更已安全的核准。
