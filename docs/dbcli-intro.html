The Problem

把 DATABASE_URL 直接餵給 Agent，是在賭什麼？

Vibe coding 最爽的時刻，是 Agent 幫你把資料撈出來、把 bug 修掉。 最痛的時刻，是它猜錯欄位名寫出一坨錯誤查詢、把密碼印進對話紀錄， 或是一句沒有 WHERE 的 UPDATE 掃過整張表。

憑證直接進了對話

連線字串貼進 prompt、寫進專案設定檔，等於把 production 密碼交給每一次對話、每一次 commit。

Agent 用猜的寫 SQL

欄位叫 user_name 還是 username？ 猜錯就是查不到，或更糟 —— 查到不該查的。

寫入沒有安全網

沒有 dry-run、沒有權限分級、沒有稽核紀錄。一句失控的 DELETE，你只能去翻備份。

賣點 1 · Credential Isolation

帳號密碼隔離：Agent 拿得到資料，拿不到鑰匙

這是 dbcli 和「直接給 Agent 一條連線字串」最根本的差異。 憑證由 dbcli 管理，Agent 只呼叫指令、只看到結果 —— 密碼從不流經對話上下文。

設定不放專案目錄

完整連線設定存在 ~/.config/dbcli/projects/<id>/， 專案裡只留一個不含機敏內容的 binding stub。不會被 Agent 掃到，也不會誤 commit 進 git。

env-refs：連設定檔都沒有明文

init --use-env-refs 把憑證存成 {"$env": "DB_PASSWORD"} 執行期才解析的參照， 適合 CI/CD 與多環境。CI 缺 key 直接報錯，絕不默默 fallback 成明文。

任何輸出都不吐憑證

status、doctor、錯誤訊息、稽核紀錄 —— 所有給 Agent 看的輸出都經過設計，連線字串與密碼一律不出現。

多連線、各自的權限等級

本地、staging、prod 是同專案裡的具名連線，各自獨立憑證、獨立權限、 獨立 schema 快取。最常見的配置：本地開 read-write 放手讓 Agent 實驗， prod 鎖 query-only —— 想寫也寫不了。

本地放心寫，線上鎖唯讀 —— 一個專案、兩條連線、兩種權限 
# 本地 DB：開發用，允許寫入
$ dbcli init --conn-name local --env-file .env.local --permission read-write

# 線上 DB：唯讀 + 憑證用 $env 參照，設定檔裡沒有明文密碼
$ dbcli init --conn-name prod --env-file .env.production \
    --use-env-refs --permission query-only

$ dbcli use local                          # 平常預設操作本地
$ dbcli query --use prod "SELECT …"        # 需要時單次指向線上，只能讀
$ dbcli update --use prod orders …
✗ Permission denied: connection "prod" is query-only

權限跟著連線走，不是跟著對話走 —— 無論 Agent 被 prompt 成什麼樣子， 對 prod 的寫入在 dbcli 這一層就被拒絕。Debug 時 Agent 可以自由對照兩邊資料， 卻不可能「順手」改到線上。

賣點 2 · Sensitive Data Blacklist

敏感欄位黑名單：AI 看不到，就洩漏不了

把 password、token、個資欄位加入 blacklist， 查詢結果在回到 Agent 之前就被遮罩 —— 包含報表與 HTML dashboard。 支援 SQL 欄位/資料表、MongoDB 巢狀 dot-path 萬用字元、Redis key glob。

blacklist 實際效果 
$ dbcli blacklist column add users.password
$ dbcli blacklist table add 'secrets:*'          # Redis key glob 也支援
$ dbcli query "SELECT id, email, password FROM users LIMIT 2"
┌────┬──────────────────┬──────────────┐
│ id │ email            │ password     │
├────┼──────────────────┼──────────────┤
│ 1  │ a@example.com    │ [REDACTED]   │
│ 2  │ b@example.com    │ [REDACTED]   │
└────┴──────────────────┴──────────────┘
賣點 3 · Layered Safety

四級權限 + 全程安全網，寫入不再是一場豪賭

預設 query-only，Agent 想做什麼，就給到哪一級 —— 一個 flag 的事。 即使開放寫入，每一步仍有護欄。

query-only預設。SELECT、list、schema、export。查詢自動加 LIMIT 1000，Agent 掃不垮你的表。
read-write+ INSERT、UPDATE。所有寫入先 --dry-run 預覽參數化 SQL 再執行。
data-admin+ DELETE（僅 DML）。--where 為必填且刻意限制為等值條件，防止範圍誤殺。
admin+ DDL。migrate 預設就是 dry-run，要 --execute 才真的動手；DROP 還要再加 --force。

Audit log 全程留痕

每個操作留下 metadata 稽核紀錄（不含 SQL 內文與資料值），跨 session 可回溯「Agent 到底做了什麼」。

失敗自動產生復原計畫

指令加 --recovery，失敗時自動存下結構化復原方案； dbcli recover --apply 在風險分級下執行安全修復步驟。

靜態風險分析

dbcli plan 不連線就能分類一句 SQL 的風險等級； Elasticsearch 更是整個唯讀，想寫也寫不了。

賣點 4 · Agent-Native

不只安全，Agent 用起來是真的順

dbcli 不是「一支普通 CLI 剛好能被 Agent 呼叫」，而是每個輸出、每個工作流都為 Agent 設計。 一行 dbcli skill --install claude，Agent 就自帶完整使用手冊。

Schema 探索，杜絕欄位用猜的

schema users --format json 給出真實欄位、預估列數、大小分級。 Skill 明文規定：禁止猜欄位名，先查 schema。MongoDB 用取樣推 dot-path 結構，Redis 看 key 型別/TTL。

Task Packs：現成的專家工作流

「診斷慢查詢」「稽核權限」「安全 backfill」「schema 漂移檢查」… skill tasks plan 直接產出一份帶風險標籤的逐步計畫，Agent 照做就好，不必自己發明步驟。

一句話變出互動式報表

q @analytics/revenue --ui 直接在瀏覽器開出含 KPI 卡與圖表的 HTML dashboard（React + Recharts、單檔可分享）。blacklist 遮罩在渲染前就完成。

可重用的參數化查詢

Saved queries 存在 repo 裡（local / 團隊共享 / 內建 @diag/* 三層）， Agent 用 queries suggest 依意圖找到現成 SQL，而不是每次重寫。

guide / report：診斷有 SOP

guide slow-query 給出確定性的下一步指令； report --section perf 一次跑完慢查詢、索引使用率、cache 命中率體檢。

七大平台 skill 一鍵安裝

Claude Code、Cursor、Copilot、Gemini、Codex、Windsurf、Antigravity —— skill --install <platform> 把工作流與完整參考文件裝進對應目錄。

你用說的，Agent 動手 —— 這就是裝上 skill 之後的日常

FAQ

常見問題

我不會寫 SQL，這工具跟我有關嗎？

正是為你設計的。你用自然語言請 Agent 處理資料，dbcli 負責讓這件事安全發生： Agent 透過 schema 確認真實結構、透過 saved queries 與 task packs 使用現成的專家查詢， 而你不需要看得懂中間的 SQL —— 只需要看得懂結果。

Agent 會不會不小心刪掉我的資料？

預設權限是 query-only，連 INSERT 都做不了。就算你開到 data-admin，DELETE 仍強制要求 WHERE 條件、建議先 dry-run， 且等值限制讓「一句掃全表」在語法層就被擋下。DDL 更要 admin + --execute + DROP 加 --force 三重確認。

支援哪些資料庫？

MySQL、PostgreSQL、MariaDB、MongoDB、Redis、Elasticsearch， 同一專案可同時設定多條具名連線（staging / prod / 分租戶），各自獨立的憑證、權限與 schema 快取。

跟直接用 MCP database server 差在哪？

dbcli 是「權限與資料防護內建」的一層：憑證隔離、blacklist 遮罩、權限分級、dry-run、 audit、recovery 全部開箱即用，且同一支 CLI 通吃七個 Agent 平台 —— 不綁定任何單一協定或編輯器， 人類自己在終端機也能用。

Plugin 和 skill --install 該選哪個？

都會裝進同一份 skill（工作流 + 完整參考文件），效果相同。差別在入口： plugin 從 agent 內的 marketplace 一鍵安裝，還內建 bunx fallback，不用先全域安裝 CLI，最適合快速試用； skill --install 適合已全域安裝 dbcli 的人， 一支 CLI 就能佈署到七個平台，也方便版本升級時同步更新 skill 文件。

team 協作怎麼辦？

Saved queries 可放 .dbcli-shared/ 進 git 與團隊共享； 憑證則走 --use-env-refs，每個人 / 每條 CI pipeline 用自己的環境變數， repo 裡永遠沒有明文密碼。
