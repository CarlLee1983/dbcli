Data correction · SQL

Before a backfill, prove that it deserves to run.

“Fill in the missing status” sounds simple, but it has a target, a scope, sensitive fields, and a condition that must be true afterward. dbcli lets an agent prepare reviewable evidence before returning the write decision to you.

Situation: You need to set the missing status in customers to active. The question is not whether an UPDATE can be written; it is whether the target is right, how much it touches, and how success will be proven.

A safe workflow

Check the protected surface first

Start with the blacklist. If the table or a field is protected, resolve the access and data policy rather than rewriting SQL around it.

dbcli blacklist list

Confirm the target from the real schema

Have the agent read the live columns and types instead of mapping a natural-language request to an imagined structure.

dbcli schema customers --format json

Preflight the UPDATE and its read-back assertion

Preflight checks that the UPDATE target matches --table, contains a WHERE clause, and uses a plain SELECT for read-back. It prints a copyable after-write command.

dbcli verify safe-backfill \
  --table customers \
  --query "UPDATE customers SET status = 'active' WHERE status IS NULL" \
  --verify-query "SELECT count(*)::int AS n FROM customers WHERE status IS NULL" \
  --expect "value == 0"

Write only after approval, then verify

Review the preflight output and execute the approved write through your team’s established authorization flow. Then run the generated command with --after-write to read back the result and write an inspectable verification artifact.

dbcli verify safe-backfill ... --after-write
dbcli verification list

What dbcli will not do for you

verify safe-backfill never executes an UPDATE. It only preflights, or verifies by reading back after a write. A ready preflight means the guards passed; it does not mean the data is verified.
