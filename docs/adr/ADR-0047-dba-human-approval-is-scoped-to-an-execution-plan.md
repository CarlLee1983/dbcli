# DBA 人工批准綁定執行計畫，由 Role Skill 保存與交接

* Status: accepted
* Date: 2026-10-17
* Decision: [#236](https://github.com/CarlLee1983/dbcli/issues/236)，於本次設計訪談確認。

延續 [ADR-0045](ADR-0045-the-dba-role-skill-lives-outside-dbcli.md) 與
[ADR-0046](ADR-0046-dba-conclusions-reference-tool-evidence.md)，`dba-skill` 管理
跨 dbcli、AWS CLI 與人工操作的批准紀錄，引用對話或外部變更單作為決定來源。
不把某個變更單系統設為必要依賴，也不把 dbcli write gate 當成工作流程批准：
前者限制批准來源，後者只處理工具執行時的確認，無法代表跨工具計畫獲准。

## 批准範圍與批准點

批准綁定具體計畫版本、環境、資源與操作，限定本次執行及明確時間窗。
超出範圍或計畫有實質變更時，必須重新批准；不能把一句「可以繼續」解讀為
後續所有操作皆獲准。例如 staging 的還原演練批准不能沿用於 production。

runbook 事先定義必要批准點。agent 遇到未涵蓋的風險或範圍變更，可以追加暫停，
不能自行取消既定批准點。runbook 或專案政策指定有權批准的人或角色，以及
可接受的身分確認來源；agent 不自行授予權限。無法確認批准資格時維持阻擋，
指出需要誰接手；單純填入姓名不算身分驗證。

批准不自動延用到下次執行。重試必須在原批准明確允許的範圍內；過期、撤回或
條件改變後，尚未執行的相關操作停止，必須重新取得批准。

## 批准內容與紀錄

批准前提供操作目的、環境與資源、計畫版本、預期影響、主要風險、回復方式或
不可逆性，以及時間窗與重試限制。批准紀錄引用這份確定的內容，保留批准者、
決定、時間、條件與來源；敏感原始資料不直接複製進紀錄。

批准紀錄與 dbcli write gate 各自檢查、不能互相替代。工作流程已批准，不會繞過
工具的權限、確認或其他執行檢查；`--yes`、輸入確認文字或工具放行，也不證明
工作流程已獲有權者批准。不擴充 dbcli operation envelope 或 evidence receipt。

## 執行交接與失效

批准不直接觸發執行。交接明確指定執行者與待執行步驟；接手時重新確認批准仍
有效、目標與計畫一致、前置條件成立。批准後尚待執行時，記錄「等待執行」的
原因、解除條件與交接對象；執行後另交回操作與驗證證據。

原決定保留，拒絕、撤回與後續決定追加記錄，不覆寫歷史。拒絕或撤回後阻擋尚未
開始的相關步驟；已開始的操作依預先定義的安全停止方式處理，不能假設可立即
中斷或自動回滾。撤回批准不代表已執行的變更已被還原。

## 批准證據與工作結論

批准只證明指定範圍內的操作獲准，不證明操作成功、備份可還原或 RPO／RTO 達標。
必要批准缺失、遭拒或失效時，相關步驟記錄阻擋原因；等待批准與等待執行分開
記錄。工作流程結果引用批准紀錄，各主張仍依 ADR-0046 的證據與判定順序得出
結論，不把整份結果一律改成 `blocked`，也不抹去已成立的 `not-met`。

## 後續邊界

本次只記錄批准語意、責任與交接，不表示批准機制已實作。
精確欄位名稱、格式、保存與身分確認機制、驗證器及執行機制由後續 Warrant Story
規格化；不新增 CLI 或批准服務，也不更改 dbcli 的公開契約。
若未來要把工具確認視為工作流程批准，或讓批准自動觸發執行，必須重新審視本決策。
