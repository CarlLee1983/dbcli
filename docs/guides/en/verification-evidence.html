Post-write verification · Provenance

After an approved write, retain evidence of what verification observed.

The write decision belongs to your authorization process. Once that work is complete, dbcli can read back the expected state, persist a verification artifact, and record safe provenance for later review.

Situation: A reviewed data correction has been performed outside dbcli. The team now needs a repeatable read-back check and a shareable record that does not expose SQL, rows, credentials, or user paths.

A safe workflow

Preflight the verification before the write

Use a supported verification scenario to check the target and read-back assertion. Preflight does not execute an UPDATE and does not create an executed-result receipt.

dbcli verify safe-backfill --table customers --query "UPDATE customers SET status = 'active' WHERE status IS NULL" --verify-query "SELECT count(*)::int AS n FROM customers WHERE status IS NULL" --expect "value == 0"

Verify after the separately approved write

Run the generated verification with --after-write to persist the resulting artifact, then write an evidence receipt to a workspace-relative path.

dbcli verify safe-backfill ... --after-write --evidence-receipt .dbcli/evidence/verify-receipt.json
dbcli verification list

Use the result with its proper meaning

The artifact records the verification outcome. The receipt records safe provenance after the verdict, audit attempt, and optional artifact are authoritative; its success or failure is distinct from authorization.

What dbcli will not do for you

An evidence receipt is not execution approval. It is unavailable in preflight mode, contains no SQL or rows, and neither scenario verification nor receipt creation executes a write or DDL.
