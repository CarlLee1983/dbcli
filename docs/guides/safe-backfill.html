資料修正 · SQL

回填資料前，先證明它值得被執行。

「把缺少的狀態補上」聽起來簡單，但它同時涉及目標表、影響範圍、敏感欄位與完成後的驗證。dbcli 讓 Agent 先產生可審查的證據，再把寫入決定交還給你。

情境：你需要將 customers 裡尚未設定的狀態補成 active。問題不是「能不能寫 UPDATE」，而是「目標正不正確、會影響多少筆、寫完後怎麼證明結果」。

安全工作流

先檢查保護範圍

從黑名單開始。若目標表或欄位受保護，先處理權限與資料政策，而不是改寫 SQL 繞過它。

dbcli blacklist list

以實際 schema 確認目標

要求 Agent 讀取正式的欄位與型別，避免把自然語言需求硬套到想像中的資料結構。

dbcli schema customers --format json

預檢 UPDATE 與回讀斷言

預檢確認 UPDATE 目標與 --table 一致、含 WHERE 條件，並檢查回讀查詢是純 SELECT。它會輸出可複製的 after-write 驗證指令。

dbcli verify safe-backfill \
  --table customers \
  --query "UPDATE customers SET status = 'active' WHERE status IS NULL" \
  --verify-query "SELECT count(*)::int AS n FROM customers WHERE status IS NULL" \
  --expect "value == 0"

人工核准後才執行寫入，再驗證

檢閱預檢結果並依團隊既有的授權流程執行核准的寫入。完成後，使用預檢產生的命令加上 --after-write 執行回讀；結果會寫成可檢視的驗證文物。

dbcli verify safe-backfill ... --after-write
dbcli verification list

dbcli 不會替你做什麼

verify safe-backfill 永遠不會執行 UPDATE。它只做預檢，或在寫入後進行回讀驗證。預檢的 ready 表示防護通過，不等於資料已被驗證正確。

下一步

需要完整旗標、結果狀態與 SQL 引擎限制時，請查看使用者文件的 verify safe-backfill 說明。
