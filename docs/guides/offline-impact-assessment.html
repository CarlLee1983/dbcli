變更審查

Schema 要改之前，先知道哪些證據會受到影響。

先把設計與本機 baseline 對照，取得有限但可檢閱的影響報告。

情境：團隊計畫刪除欄位、調整型別或改變關聯；需要在 migration review 前辨認已知依賴。

安全工作流

選定一個本機 baseline

以既有 schema cache 或明確指定的 ORM artifact 為比較基準；每次 assessment 必須剛好選一種。

dbcli impact assess --design ./dbcli.design.json --against-cache --output ./impact.json --format json --fail-on warn

離線比較 ORM

如果變更仍在 application model 階段，可以指定 ORM 檔案；這條路徑完全讀取本機 artifact。

dbcli impact assess --design ./dbcli.design.json --against-orm ./prisma/schema.prisma --output ./impact.md --format markdown --fail-on never

把 coverage gap 一起帶進審查

報告會使用可用的 semantic contracts、saved-query 名稱、verification metadata 與選用的已審閱 workload evidence。缺少、過期或無法讀取的證據會列為 partial coverage gap。

dbcli 不會替你做什麼

impact assess 不會連線、不會執行 SQL、不會更新 cache，也不會讀取 query body。v1 永不宣稱覆蓋完整；報告不是變更已安全的核准。

下一步

檢閱設計與影響評估文件，再由團隊決定 migration 與寫入後驗證。
