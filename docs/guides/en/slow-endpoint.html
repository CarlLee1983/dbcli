Performance investigation · SQL

The first step on a slow API is not guessing a missing index.

Letting an agent tune production directly is a risky shortcut. Aggregate observed activity, inspect the query plan, and generate reviewable index guidance before narrowing the cause.

Situation: An API slows down at peak time. You need to know whether the same SQL repeats, which tables the slowest queries touch, and what to check before changing anything.

A safe workflow

Find patterns from local observation events

proxy analyze reads recorded events and aggregates fingerprints, durations, errors, and hot tables. It does not perform database writes.

dbcli proxy analyze --format json --top 10

Confirm structure, then inspect the query plan

Confirm the live schema of the affected table, then gather execution evidence with explain.

dbcli schema orders --format json
dbcli explain "@saved-query" --format markdown

Keep index proposals in review

Get missing-index guidance for the confirmed query, then let migration review decide whether it should become DDL.

dbcli guide missing-index-for "@saved-query" --format json
dbcli skill tasks plan migration-review \
  --param "table=<exact table name>" \
  --param "ddl=<captured dry-run DDL>"

What dbcli will not do for you

It will not create an index from a single query, nor treat observation as a performance conclusion. Indexes affect write cost, locking, and deployment strategy, so people should review them.
