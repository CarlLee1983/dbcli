# dbcli GitHub Pages 產品化改版設計

日期：2026-07-18

## 背景

目前 `docs/dbcli-intro.html` 與 `docs/dbcli-intro.en.html` 已完整介紹 dbcli，但首屏以深色終端機、安裝指令、安全風險與大量技術能力切入。整體容易被理解成 API 或開發文件，訪客尚未感受到產品成果，就必須先消化工具術語。

本次改版不縮減 dbcli 的技術深度，而是重排理解順序：先展示 AI Agent 如何更快完成一個真實資料任務，再同步揭示 dbcli 在背後提供的安全邊界，最後才展開安裝方式與技術細節。

## 目標

- 第一眼建立「效率與安全兼得」的產品定位。
- 讓訪客先看見一段完整工作流程，再決定是否安裝。
- 降低 API 文件感、終端機感與同質卡片造成的認知負擔。
- 保留工程師需要的可信度、具體能力與可驗證細節。
- 維持中英文頁面、靜態 HTML 與既有 GitHub Pages 發佈方式。

## 非目標

- 不改變 CLI 行為、安裝機制或 GitHub Pages 發佈來源。
- 不新增前端框架、服務端功能或資料收集。
- 不把「不熟資料庫」設定為唯一受眾或主要定位。
- 不刪除完整文件；首頁只負責建立理解與導流。

## 受眾與核心訊息

主要受眾是使用 AI Agent 進行 vibe coding 或軟體開發、希望更快完成資料工作，同時不願犧牲安全性的開發者。

核心訊息：

> 你說目標，Agent 完成。資料安全交給 dbcli。

「不熟資料庫也能使用」是輔助亮點。主要價值是減少反覆確認、避免猜測 schema、縮短從需求到結果的流程，並以權限、敏感資料保護、風險預覽、驗證與稽核維持安全邊界。

## 選定方向

### 資訊架構：對話 × 防護

使用者可見的效率與 dbcli 背後執行的安全措施並列呈現：

- 左側：自然語言需求、Agent 回應與最後成果。
- 右側：schema 確認、敏感欄位保護、權限限制、風險檢查、結果驗證與稽核紀錄。

此結構讓訪客不用先理解指令，即可同時看懂「完成了什麼」與「為什麼可以放心」。

### 美術方向：友善產品感

- 奶油白作為主要背景。
- 柔和橘與霧藍作為品牌色塊，深棕黑作為正文色。
- 大標題、短句與明顯留白取代高密度資訊。
- 圓潤卡片、細邊框與低對比陰影建立層次。
- 使用一致的線性圖示，不混用 emoji、模型生成 SVG 或過多技術符號。
- 深色終端機只在需要證明技術細節時局部出現，不再主導整體視覺。

## 頁面結構

### 1. 導覽列

- dbcli 品牌名稱。
- 錨點：怎麼運作、安全設計、支援平台。
- 主要按鈕：開始使用。
- 中英文切換保留為清楚但次要的入口。

### 2. Hero：成果承諾

- 主標題：「你說目標，Agent 完成。資料安全交給 dbcli。」
- 副標題聚焦從分析到報表的效率，以及 dbcli 全程守住資料界線。
- 主要 CTA：「看看它怎麼運作」，捲動至實際流程。
- 次要 CTA：「前往 GitHub」。
- 不在首屏放安裝指令。
- 首屏主視覺是「對話 × 防護」雙欄：
  - 對話側展示一個具體分析需求與完成結果。
  - 防護側同步展示 dbcli 背後完成的安全步驟。

### 3. 實際工作流程

以單一連貫情境展示：

1. 使用者以自然語言提出分析需求。
2. Agent 透過 dbcli 確認 schema，而非猜測欄位。
3. dbcli 套用黑名單、權限與查詢限制。
4. Agent 執行查詢並由 dbcli 驗證結果。
5. 最後產出可分享的互動式報表。

此區優先呈現成果與時間節省，技術指令作為可展開的佐證。

### 4. 效率價值

以三個差異化能力說明效率：

- 一次描述目標，Agent 能完成探索、查詢、驗證與輸出。
- schema 與可重用 queries 減少猜測及反覆來回。
- guide、recovery 與 report 讓診斷和交付有可重複流程。

避免用完整 command list 取代價值說明。

### 5. 安全設計

將安全能力整理成可理解的防護層：

- 憑證與工作區隔離。
- 敏感欄位黑名單。
- 分級權限與 dry run。
- 風險分析、驗證、復原與稽核。

先說明每層降低什麼風險，再提供對應指令或技術細節。

### 6. 支援範圍

- 資料庫：PostgreSQL、MySQL、MariaDB、MongoDB、Redis、Elasticsearch。
- Agent 與開發平台：依目前實際支援項目呈現。
- 使用品牌名稱與一致的文字標籤，避免過多 badge 造成視覺噪音。

### 7. 安裝與開始使用

- Plugin／Skill 安裝為主要路徑。
- CLI 安裝為次要路徑。
- GitHub 與完整文件為延伸入口。
- 安裝指令提供複製操作；即使 JavaScript 不可用，文字仍可選取與複製。

### 8. FAQ 與頁尾

- FAQ 保留最常阻礙導入的問題，不重複完整文件。
- 最終 CTA 呼應「效率 × 安全」，不以恐嚇式風險文案收尾。
- 頁尾提供 GitHub、文件、語言切換與授權資訊。

## 元件與互動

- 導覽列、按鈕、標籤、流程步驟、對話卡、防護清單、能力卡、安裝卡與 FAQ 使用一致的視覺規則。
- Hero 流程可使用輕量 CSS 動畫：對話出現後，防護項目依序完成，最後顯示成果。
- 動畫不承載唯一資訊；`prefers-reduced-motion: reduce` 時直接顯示完成狀態。
- FAQ 使用原生 `details` / `summary`。
- 錨點捲動需考慮固定導覽列偏移。
- 所有互動元素提供 hover、focus-visible 與 active 狀態。

## 響應式設計

- 桌面：Hero 與實際流程採雙欄。
- 平板：縮小欄距與字級，仍可維持雙欄時不壓縮可讀性。
- 手機：改為單欄，依序顯示使用者需求、Agent 成果、背後防護，維持故事順序。
- 導覽在小尺寸隱藏次要錨點，但主要 CTA 與語言入口仍可操作。
- 不使用依賴固定高度的內容容器，避免中英文換行造成截斷。

## 中英文一致性

- `docs/dbcli-intro.html` 與 `docs/dbcli-intro.en.html` 使用相同區塊順序、元件結構與能力範圍。
- 文案採語意一致而非逐字翻譯，允許因語言長度調整換行。
- 任一功能、CTA、連結或支援平台變更都必須同步更新兩頁。

## 可用性與無障礙

- 使用語意化的 `header`、`nav`、`main`、`section` 與 `footer`。
- 文字和互動元素維持可辨識的色彩對比。
- 鍵盤可到達所有連結、複製按鈕與可展開內容。
- 圖片提供有意義的替代文字；純裝飾元素不進入無障礙樹。
- 點擊區域適合觸控操作。

## 效能與相容性

- 維持自包含靜態 HTML，不新增前端框架或執行期依賴。
- 優先使用 CSS 形狀、排版與現有資產；只有具資訊價值的圖片才載入。
- 非首屏圖片設定尺寸與 lazy loading，降低版面跳動。
- JavaScript 僅用於漸進增強；內容與導覽在腳本失效時仍可使用。
- 相對資源路徑必須在本機檔案預覽與 GitHub Pages 子路徑下皆有效。

## 驗收方式

- 驗證中英文頁面結構與功能敘述一致。
- 驗證所有相對連結、錨點、圖片與語言切換。
- 執行 HTML 結構檢查與現有文件檢查。
- 檢查桌面、平板、手機主要 viewport：
  - 首屏先呈現成果，而非安裝或 API 細節。
  - 「對話 × 防護」關係一眼可理解。
  - 雙欄轉單欄後故事順序正確。
  - 無文字溢出、內容截斷或水平捲動。
- 使用鍵盤走查主要操作，確認 focus 狀態與 FAQ。
- 在 reduced-motion 設定下確認內容完整。
- 確認沒有引入不必要的大型資產或第三方套件。

## 完成定義

- 中英文 GitHub Pages 首頁均完成改版並保持功能對等。
- 首屏以真實工作流程表達效率與安全，不再以安裝指令或風險清單主導。
- 視覺採已確認的友善產品感，且在主要 viewport 通過人工檢視。
- 既有 GitHub Pages 發佈方式與相對路徑維持可用。
- 驗收項目全部通過，且沒有未填內容、待辦標記或語意矛盾。
